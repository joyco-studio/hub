We had a calibrated simulator that could say an encounter had a 17% chance of a character dying. We
also wanted the product to explain *why*: the enemies have the action advantage, one character is
vulnerable to a one-hit knockout, and disciplined opponents can remain credible without fighting to
the death.

That sounds like an ideal LLM feature. Give the model the party and the monsters, then ask it to
analyze the fight.

It is also how you quietly replace a tested product with plausible prose.

The boundary we settled on is simple:

> The engine owns facts. The model owns language.

## Do not ask the model a question your code can answer

If an LLM receives raw domain state and returns the verdict, it becomes an uncalibrated second
calculator:

```txt
party + enemies → LLM → “Deadly, roughly 20% death risk”
```

The percentage may be reasonable. It may even match the simulator today. But it has no stable
relationship to the tests that validate hit chance, damage distributions, targeting behavior,
healing, or the thousands of combat runs behind the real number. A provider or model upgrade can
change the answer without touching application code.

Prompting it to “be accurate” does not connect it to those contracts.

Instead, calculate first and give the model a closed set of facts to explain:

```txt
user state
  → deterministic rules + seeded simulation
  → typed analysis facts
      ├─→ UI renders numbers directly
      ├─→ local explanation fallback
      └─→ LLM writes constrained prose
```

The model is downstream of truth. It never sits on the path that creates truth.

## Build a typed fact packet

Do not dump internal application state into the prompt and hope the model finds the important parts.
Build a deliberate transfer object containing only established facts and the uncertainty the product
has chosen to expose:

```ts
const InsightInput = z.object({
  officialBand: z.string(),
  riskTier: z.enum(['manageable', 'hard', 'deadly', 'extreme', 'impossible']),
  droppedRate: z.number().finite(),
  deathRate: z.number().finite(),
  wipeRate: z.number().finite(),
  droppedRateAtLowPartyDamage: z.number().finite(),
  droppedRateAtHighPartyDamage: z.number().finite(),
  actionEconomy: z.number().finite(),
  topOneShotRisks: z.array(OneShotRisk),
  verifiedFixes: z.array(VerifiedFix),
  usesApproximateData: z.boolean(),
})
```

This packet is not a convenience DTO. It is the authority boundary.

- Every number came from application code.
- Every field has explicit semantics.
- Unknown or non-finite values cannot slip through as `NaN` and become prose.
- Approximate inputs carry provenance, so the explanation can name uncertainty honestly.
- Facts the model does not need never enter its context.

The packet should be validated at the API boundary even if the client constructed it. Server-side
validation prevents partial, outdated, or hand-written requests from turning the model into a more
permissive alternate endpoint.

## Shape the output around language, not duplicated facts

The model output schema should contain the things language models are useful for:

```ts
const Insight = z.object({
  verdict: z.string(),
  drivers: z.array(CausalDriver).min(2).max(4),
  tactics: z.array(RealisticTactic).min(2).max(4),
  narrativeWorkarounds: z.array(Workaround).max(3),
  flavor: z.string(),
})
```

Notice what is absent: no computed risk tier, no replacement percentage, no new balance fix. The UI
already has those values and renders them from the deterministic analysis. Asking the model to echo
them would create two sources of truth and force the UI to decide which one wins when they disagree.

This complements [Understanding the Agentic Chat Model](/logs/18-understanding-the-agentic-chat-model):
structured message parts answer who owns live conversation state; this boundary answers who owns the
claims inside the conversation.

## Render facts and prose as separate provenance

The user should not need to reverse-engineer which sentence was calculated and which was generated.
Keep verified recommendations in their own UI, driven by their own structured records. Keep the LLM's
tactics and flavor in the explanation surface. Do not bury both inside one markdown blob.

This separation also protects interaction. A verified recommendation can carry a structured,
revision-guarded Apply action. A model-authored tactic is advice. Giving both the same visual and
behavioral affordance would grant generated text authority it never earned.

## Prompts state the contract; architecture enforces it

The prompt should still say the rule plainly:

```txt
The deterministic calculator has already decided the risk tier and verified
the balance fixes. Explain those facts; never replace them with your own math.

Use only numbers present in DATA. Never invent a percentage, damage value,
score, or predicted effect. Do not propose additional calculated fixes.
```

That improves output quality, but the prompt is not the boundary. The boundary is structural:

1. The model never receives authority to write calculated state.
2. Its schema has no field for replacement calculations.
3. Verified numbers render from engine output, not model output.
4. The application can operate without a model response.

If correctness depends only on the model obeying a sentence in a prompt, correctness is probabilistic.

## Schema validation is necessary and insufficient

A structured response can be syntactically perfect and still violate product policy. For example, a
model can return exactly two tactics with every required string while recommending that the user
replace a player character or increase the party's level. The schema cannot tell whether that crosses
a domain boundary.

Add semantic validation for invariants important enough to reject the response:

```ts
const parsed = Insight.safeParse(modelOutput)
if (!parsed.success) return fallback

if (recommendsChangingImmutableParty(parsed.data)) {
  return fallback
}
```

Some invariants are safer to enforce with code after generation. If narrative workarounds are legal
only for an impossible scenario, clear the array for every other case regardless of what the model
returned. If an impossible scenario requires at least two alternatives, reject a response that omits
them.

Use the schema for shape, semantic guards for meaning, and deterministic post-processing for
non-negotiable state.

## The model must be additive

An API key can be missing. A provider can time out. Structured generation can fail. A model can
return a valid shape that violates a semantic invariant. None of those should remove the engine's
analysis from the page.

Build a local explanation from the same fact packet:

```ts
const fallback = buildFallbackInsight(input)

const insight = await requestModel(input).catch(() => fallback)
```

The fallback does not need to imitate the model. It needs to preserve the product contract: state the
calculated tier, name deterministic drivers, and offer conservative tactics derived from known enemy
behavior. The LLM adds specificity, synthesis, and better writing when available.

This gives the feature a clean degradation ladder:

```txt
engine facts + model prose
engine facts + local prose
engine facts only
```

There is no rung where the product has prose but loses its facts.

## Regeneration should not destroy a good answer

The same additive principle applies during retry. If the user regenerates an explanation and the new
request fails, do not overwrite a valid prior model response with a weaker fallback. Keep the prior
response visible and surface the retry failure separately.

This is a small detail with a large effect on trust. “Try again” should not destroy the best result the
system already has.

Track provenance explicitly:

```ts
type Provenance =
  | 'model'
  | 'fallback-no-key'
  | 'fallback-error'
```

Provenance controls the label and retry behavior. It does not change the calculated facts, because
those never belonged to the explanation layer.

## Be explicit about what was not measured

The model is good at connecting supplied facts to real-world tactics, but that fluency can blur the
line between measured and merely plausible. If the simulator does not model terrain, positioning,
morale, line of sight, or concentration, the prompt must forbid language that presents their effects
as calculated.

The model may say “cover could reduce incoming pressure.” It may not say “cover lowers death risk to
9%” unless 9% exists in the fact packet from a simulation that actually modeled cover.

This is not a disclaimer pasted below the output. It is part of the epistemic contract: suggestions can
reach beyond the model, measurements cannot.

## When this split is useful

Use this pattern whenever deterministic or externally verified logic already owns the answer: finance
calculators, analytics, diagnostics, eligibility rules, scheduling constraints, security findings,
scientific models, and recommendation engines. Let the LLM summarize, prioritize, translate, and
explain. Do not let it quietly recalculate.

If the task itself has no deterministic answer—brainstorming a name, drafting copy, exploring a
strategy—the model can own more of the result. The boundary should follow the product's source of
truth, not a blanket rule that AI must always be decorative.

## The rule

> Calculate facts before generation, pass the model a validated and provenance-aware fact packet,
> constrain its output to language-shaped work, enforce semantic invariants in code, and keep a local
> path that preserves the product when generation disappears.

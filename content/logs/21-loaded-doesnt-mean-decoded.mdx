The investigation began with a narrow question: whether AVIF or WebP was faster
in a Canvas image sequence. The codec benchmark answered the transfer-size part,
but the performance traces exposed a more important problem: **an image can be
downloaded, cached, and complete without its decoded pixels still being in
memory**.

That distinction changes how an image-sequence player should be designed.

In the 86-frame sequence, AVIF transferred fewer bytes than WebP. Around
`ctx.drawImage()`, however, both codecs had a p95 of roughly `0.1 ms`, too close
to the timer resolution to claim a synchronous drawing winner. Enabling
responsive sources then increased the selected frame width from 640 to 1080
pixels. Stable playback started re-decoding almost every frame and producing a
partially presented frame at almost the same rate.

The codec had not suddenly become slow. The decoded-image working set had been
exceeded.

## There are two image sizes

The size shown in Network is the **encoded** size: the AVIF or WebP bytes sent
over the wire. Once decoded for display, both become a pixel buffer whose rough
size is:

```txt
width × height × 4 bytes
```

For square RGBA frames, that made the sequence approximately:

| Frame size | One decoded frame | 86 decoded frames |
|---|---:|---:|
| 640 × 640 | 1.56 MiB | 134 MiB |
| 1080 × 1080 | 4.45 MiB | 383 MiB |

Those are minimums. Canvas backing stores, compositor resources, GPU textures,
and the rest of the page add more pressure.

AVIF can therefore save a third of the transfer bytes and still consume about
the same decoded memory as WebP at the same dimensions. Codec and resolution
solve different problems:

- the codec controls transfer and decode characteristics;
- the pixel dimensions control the decoded working set;
- the player controls how much of that working set stays live.

## The decoded bitmap is a cache

An `HTMLImageElement` does not permanently own a decoded bitmap. The compressed
response may remain in the HTTP cache while the browser discards its decoded
pixels under memory pressure.

That gives an image at least three relevant states:

This is why `image.complete === true` is not a decoded-memory guarantee. In the
eager Canvas player, all 86 `HTMLImageElement`s still existed, but their 1080px
pixel buffers did not all remain resident. When playback looped back to an
evicted frame, `drawImage()` pulled decoding back into the presentation path.

The trace made the pattern unusually clear: both AVIF and WebP ran at about
`23.6` decodes per second in a 24 fps sequence, and almost every decode occurred
next to a partially presented frame. At 640px the same architecture produced
few or no stable-playback decodes because the much smaller working set happened
to fit.

That does not make 640px a free optimization. On a high-DPR display, a canvas
that is 630 CSS pixels wide can need well over 1080 physical pixels. Fixing the
source at 640 trades sharpness for memory. Reintroducing `srcset` correctly
restored image quality, but it also revealed that keeping every responsive
frame decoded was not a viable architecture.

## Keep a decoded window, not the whole sequence

The production player exposed the useful architecture, not a controlled
renderer win. It kept a moving window of 12 frames around the current position.

If frame 30 is visible, the window contains roughly `30…41`. When playback
advances, frame 30 leaves and frame 42 enters. At 1080px, that changes the
minimum decoded working set from about 383 MiB to about 53 MiB.

That 53 MiB is a lower-bound estimate of the pixels the application chooses to
own. It is not a promise about browser process memory, GPU memory, or how long
the browser will keep every decoded buffer resident.

Each incoming frame crosses an explicit readiness boundary:

```ts showLineNumbers
async function loadFrame(index: number, generation: number) {
  const image = new Image()
  const props = getFrameProps(index)

  image.srcset = props.srcSet
  image.sizes = props.sizes
  image.src = props.src

  await withTimeout(image.decode(), FRAME_TIMEOUT)

  if (generation !== activeGeneration || !wanted.has(index)) return
  ready.set(index, image)
}
```

`await image.decode()` does **not** block the main thread. It suspends this async
function while the browser downloads and decodes the image. Input, animation,
React, style, layout, and paint can run after the function yields. Decoding can
still contend for browser threads, CPU, and memory; the important part is that
JavaScript is not synchronously waiting for the promise in the frame that tries
to present the image.

Decode completion is not enough by itself. The frame must also still be wanted.
A resize, scroll jump, visibility change, or unmount can make an in-flight frame
obsolete before its promise resolves. Stale results should be discarded;
timeouts and failures must release their pending slots instead of retrying in a
tight loop. The preloader and visible image should also use the same final URL
and CORS mode so the browser does not create duplicate request or decode paths.

The scheduler then advances only when the next frame is ready:

```ts showLineNumbers
function tick(delta: number) {
  elapsed += delta
  if (elapsed < FRAME_DURATION) return

  const next = (current + 1) % frameCount
  const frame = ready.get(next)

  if (!frame) {
    elapsed = Math.min(elapsed, FRAME_DURATION)
    return // keep presenting the current frame
  }

  visibleImage.src = frame.currentSrc || frame.src
  current = next
  elapsed -= FRAME_DURATION
  refillWindowFrom(current)
}
```

The `return` is the playback policy. If the next frame is not ready, the player
holds the current frame and tries again on the next tick. It does not clear the
screen, present an undecoded frame, or accumulate an unlimited time debt and
then skip forward. Under a slow network the sequence may run below 24 fps, but
the rest of the page remains responsive and the user sees complete frames.

The window size and request concurrency are separate knobs. A 12-frame window
does not imply 12 simultaneous requests, and neither has anything to do with
Sharp's encoder concurrency during the build. Name and measure those settings
separately.

### Autoplay is ordered demand

For autoplay, the immediate next frame matters more than every later frame.
Fill the bounded window sequentially from the current position, advance only
when that next frame is ready, and cap accumulated time while holding so
recovery does not fast-forward through the sequence.

A binary order such as `0, 85, 42, 21…` gives early coverage across an
incomplete sequence, but it optimizes a different contract: showing the nearest
loaded approximation. It is not the default for a player that promises ordered
frames and holds when the next one is unavailable.

### Scroll is target demand

Scroll-driven playback can jump from frame 8 to frame 55, so loading frame 9
first may be wasted work. Prioritize the latest target, use the remaining window
for nearby frames biased toward the direction of travel, and cancel pending work
that is now far outside the wanted set. Coalesce scroll changes to one scheduling
decision per animation frame; during a fast scrub, reaching the latest target is
more useful than presenting every integer in between.

Loading order and decoded-frame retention are separate policies, but both must
match the kind of demand the interaction creates.

## A good player fails without going blank

The poster or first valid frame is part of the runtime contract, not decoration.
Once it appears, the sequence should never return to an empty surface or loader.
Network and decode pressure may slow animation progress, but they should not
damage page integrity.

That produces a compact set of lifecycle rules:

- show a poster before playback; do not wait for the complete sequence to make
  the component usable;
- let only a decoded, still-wanted frame replace the visible one;
- preserve the current frame while rebuilding future candidates after resize or
  orientation changes;
- pause the clock while the page is hidden and release future frames when the
  section is no longer nearby;
- show the poster under reduced motion instead of starting the playback loop;
- time out failed frames, free their pending slots, and avoid continuous retry
  loops.

## The lesson is not “Canvas blocks, images don't”

A normal Canvas 2D call is synchronous JavaScript:

```ts
ctx.drawImage(frame, 0, 0)
```

JavaScript does not regain control until that call returns, although the browser
may defer some raster or GPU work. If the decoded pixels are gone, the call can
cause enough decode work on its critical path to miss presentation deadlines.
Measuring only the duration around `drawImage()` still does not capture all
decode, raster, or GPU completion, which is why the Performance trace mattered
more than the microbenchmark.

But Canvas can use the same readiness policy:

```ts
const frame = ready.get(next)
if (!frame) return // do not clear; the previous canvas pixels remain

ctx.drawImage(frame, 0, 0)
current = next
```

It should predecode into a bounded window, draw only when the effective frame
changes, pause and cancel work offscreen, and hold when the next frame is not
ready. Canvas was not inherently incapable of doing this; the eager player
simply kept all 86 images and trusted their decoded representations to remain
resident.

`OffscreenCanvas` can move Canvas drawing into a worker, usually with
`ImageBitmap` or `ImageDecoder` instead of `HTMLImageElement`. That can keep the
`drawImage()` call off the main thread, but it does not remove the costs of
decoding, memory, transfer, rasterization, or GPU work. It is a larger
architecture, not a switch that fixes an oversized working set.

## Prefer the smallest renderer that expresses the job

For a sequence that displays one prerendered image at a time, a single `<img>`
is the more direct renderer:

- `srcset` and `sizes` are native rather than recreated around Canvas;
- `decode()` provides an explicit asynchronous readiness boundary;
- stable dimensions let `src` change without causing layout;
- the browser presents the image without an extra application-level draw step.

Replacing `src` 24 times per second is not the expensive part compared with
decoding and presenting more than a million pixels per frame.

Canvas earns its complexity when the sequence actually needs drawing:

- composing multiple images, masks, particles, or overlays;
- dynamic clipping, blending, filters, or transforms;
- procedural graphics in the same render loop;
- pixel access, export, or use as an input to another graphics API.

If the output is just one frame, Canvas is not automatically cleaner or faster.
If composition is required, keep Canvas, but still give it the decoded-window
architecture.

## Benchmark the layers separately

The original codec comparison stayed useful because it isolated codec from
player architecture:

1. Both formats were generated from the same source frames and served through
   the same static path.
2. Canvas size, scheduler, cache conditions, and browser request concurrency
   were identical.
3. Encoder configuration and encoder concurrency were fixed and recorded.
4. Cold delivery was measured separately from stable playback.
5. The timing probe wrapped only `drawImage()`, while a browser trace captured
   decode and presentation behavior outside that synchronous call.
6. The effective responsive candidate, viewport, DPR, focus, visibility, GPU
   acceleration, and timer resolution were recorded.

Codec quality numbers are not a shared perceptual scale. In that benchmark,
AVIF quality 65 / effort 3 and WebP quality 85 / alpha quality 100 reproduced
the recipes used by that version of Next.js for a requested quality of 85. That
made the pipeline comparison reproducible; it did not prove equal visual
quality. A perceptual-quality claim would need a separate calibrated or blind
comparison.

The later Canvas and production `<img>` traces answered a different question.
They used different page revisions, durations, and cache conditions, so they
were profiler diagnostics rather than a controlled renderer benchmark. They
identified decoded-memory pressure and presentation policy as mechanisms; they
did not prove that every `<img>` player is faster than every Canvas player. The
case for `<img>` here comes from its simpler, browser-native fit for presenting
one responsive image at a time.

The result was deliberately narrow: AVIF won on bytes, neither codec proved a
`drawImage()` advantage, and the later playback regression came from decoded
memory and scheduling rather than encoded format.

## The rule

> For image sequences, budget decoded pixels instead of downloaded files. Keep
> a small moving window, mark frames ready only after asynchronous decoding and
> a still-wanted check, schedule for ordered or target demand, hold the current
> frame when the next one is not ready, and use Canvas only when the visual
> result actually needs drawing.

This is the same critical-path principle described in [The Render
Pipeline](/logs/12-the-render-pipeline): expensive work is much easier to absorb
before presentation than inside the frame that needs to appear now.

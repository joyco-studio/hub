description: How to fetch, decode, and present large image sequences without putting that work on the critical frame.

An image sequence looks like one moving visual, but the browser sees dozens or
hundreds of independent images. Every displayed frame needs three things:

- **encoded bytes**, transferred from the network or an HTTP cache;
- **decoded pixels**, prepared from those compressed bytes;
- **a ready surface**, safe to reveal at the next presentation deadline.

Those stages have different budgets. Loading every file does not make every
frame ready, and keeping every `Image` object does not keep every decoded bitmap
in memory.

## Every frame has a pipeline

<Diagram index={1} title="The lifecycle of one sequence frame">{`

| State       | What exists                            | What it means                            |
| ----------- | -------------------------------------- | ---------------------------------------- |
| Transferred | Encoded AVIF or WebP bytes             | Another network request may be avoidable |
| Decoded     | A pixel representation exists          | The element can be prepared for a render |
| Presented   | A DOM or Canvas surface uses the frame | The frame is selected for the next paint |

`image.complete === true` only describes the loading state. It does not certify
that decoded pixels are resident or ready to stay resident.

Frame count limits temporal granularity. Frame count and playback cadence
together determine duration, while the playback clock determines target fps. A
24 fps clock means that a ready frame is needed every 41.67 ms. It does not give
each decode 41.67 ms of main-thread time.

## The browser can discard decoded frames

Browsers retain decoded image data within internal memory budgets and may evict
older frames when those budgets are exceeded. Holding an `Image` reference does
not reserve its decoded pixels, and the browser does not expose control over
this cache. Dropping references makes an image eligible for cleanup, but does
not force an immediate release.

This is where large eager sequences fail. All encoded responses may already be
cached, yet early frames can require another decode by the time playback loops
back to them. Attempting to reveal an `<img>` or draw to Canvas without checking
readiness can pull that decode onto the presentation path and cost frames across
the page.

The surface is not the root problem. Both `<img>` and Canvas are smooth when a
frame is prepared before presentation, and both can fail when an unprepared
frame reaches that deadline.

## Decode before the deadline

The `Image` class creates an image element without displaying it. It can prepare
future frames without exposing incomplete work:

```ts showLineNumbers
async function decodeFrame(blob: Blob, signal: AbortSignal) {
  const image = new Image()
  const src = URL.createObjectURL(blob)

  image.decoding = 'async'
  image.src = src

  try {
    await raceDecode(image.decode(), signal, FRAME_TIMEOUT)
    if (signal.aborted) throw signal.reason
    return image
  } catch (error) {
    image.removeAttribute('src')
    URL.revokeObjectURL(src)
    throw error
  }
}

function queueDecode(url: string, blob: Blob) {
  if (pending.has(url)) return

  const controller = new AbortController()
  pending.set(url, controller)

  void decodeFrame(blob, controller.signal)
    .then((frame) => {
      if (
        controller.signal.aborted ||
        pending.get(url) !== controller ||
        !wanted.has(url)
      ) {
        releaseFrame(frame)
        return
      }

      ready.set(url, frame)
    })
    .catch((error) => {
      if (!controller.signal.aborted) scheduleRetry(url, error)
    })
    .finally(() => {
      if (pending.get(url) === controller) pending.delete(url)
      pumpDecodes()
    })
}
```

`await image.decode()` suspends the async function instead of spinning until
decode finishes. Decode still consumes CPU and may use main-thread time, so its
admission must remain bounded. Pending work is keyed by resolved URL, and the
identity check prevents an obsolete completion from touching its replacement.
Cancellation is logical: clearing `src` and revoking its Blob URL retires the
job, but browser codec work may overlap briefly before it stops.

Successful `decode()` is not a permanent lease. The
[HTML `decode()` algorithm](https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-decode-dev)
asks the browser to keep decoded data through at least the next successful
rendering update, except in low-memory situations. A local `ready` entry is
therefore a short-lived readiness signal, not ownership of browser memory.

## Keep a small runway and separate transfer from decode

At 24 fps, three resident future frames provide about 125 ms of runway. This is
a useful starting point, not a universal value. The target is the smallest
window that avoids underruns on the real page.

Transfer can run farther ahead because encoded files are much smaller than
decoded pixel buffers. Decode should remain close to presentation:

```ts showLineNumbers
const policy = {
  sharedFetchConcurrency: 8,
  decodeConcurrencyPerSequence: 3,
  readyAhead: 3,
}
```

The queues should roll continuously rather than wait for rigid batches. When a
fetch finishes, the highest-priority missing response takes the free slot. Each
sequence admits only the decodes relevant to its current three-frame window.
These limits bound application demand; abandoned browser decode work can still
overlap briefly.

Priority depends on the interaction:

- **autoplay:** next frame first, then fill forward in order;
- **time-based loops:** spread transfer coverage across the range, then present
  the closest useful ready frame without moving backward in the loop;
- **scroll-driven sequences:** target frame first, then nearby frames biased
  toward scroll direction, with rapid targets coalesced to one per animation
  frame;
- **approaching sections:** poster and entry frames only, expanding the runway
  once the sequence becomes active.

Immutable frame URLs can use:

```txt
Cache-Control: public, max-age=31536000, immutable
```

The current component uses one module-level transfer manager for every instance,
with no provider setup. It deduplicates requests, retains a bounded LRU of
encoded `Blob`s, and distributes the eight slots round-robin among active
sequences. Decoded frames stay local to each player so disposal and
presentation remain simple.

## Hand off only prepared frames

The current player keeps one `<img>` mounted. Future frames decode in off-DOM
`Image` elements backed by Blob URLs; presentation assigns only a URL that has
already passed that gate:

```ts showLineNumbers
function presentFrame(frame: HTMLImageElement, index: number) {
  if (index !== wantedIndex) return false

  const releasePrevious = surfaceLease
  surfaceLease = retainSurface(frame)

  visibleImage.removeAttribute('srcset')
  visibleImage.src = frame.src
  releasePrevious?.()
  currentIndex = index

  return true
}
```

The lease keeps that Blob URL alive while the mounted image uses it. Failed,
timed-out, or superseded frames never enter the ready map, so the last valid
surface remains instead of being replaced by a loader. This handoff is a
readiness gate, not proof that pixels have physically reached the GPU.

## A runway cannot fix slow delivery

A decoded runway absorbs temporary latency. It cannot compensate when the
network provides fewer frames than playback consumes. Every finite buffer will
eventually empty, so increasing the runway only delays the stall while using
more memory.

When transfer cannot sustain the target cadence, it must start earlier, use
smaller assets, or let playback hold the poster or current frame while the
buffer recovers.

The default `hybrid` policy keeps authored time moving and presents the closest
useful ready frame. `Sequential` holds for the exact next frame instead. Both
keep the last valid surface visible when preparation loses the race.

## Handle source changes and lifecycle explicitly

Responsive source selection belongs to the scheduler. Choose a concrete URL
from rendered width and device pixel ratio, reserve the aspect ratio, and reset
the local decode window when a resize selects another variant. Keep the last
valid surface visible while the new source prepares.

The same principle applies to page lifecycle:

| Condition            | Default behavior                                                     |
| -------------------- | -------------------------------------------------------------------- |
| Reduced motion       | Keep the poster and skip speculative sequence work                   |
| Hidden document      | Stop the playback clock and suspend local decode demand              |
| Resize/source change | Retire stale work, retain the surface, then prepare the new variant  |
| Missing frame        | Hold the current frame until an acceptable replacement becomes ready |

## Tune the whole pipeline

The current player uses three future decoded frames, up to three relevant
decode promises per sequence, and eight shared transfer slots. Measure
request-to-ready, holds, skips, and dropped frames on the real page before
changing those limits. More concurrency helps only while it improves throughput
without starving other work.

The [Render Pipeline](/logs/12-the-render-pipeline) explains how preparation can
compete with JavaScript, style, layout, and paint. The
[Performance Monitor](/logs/09-performance-monitor) helps observe that behavior
without turning this player into its own diagnostics system.

## The rule

> Fetch encoded frames ahead, decode only the frames relevant to current demand,
> and assign only prepared Blob URLs. Keep the decoded window small, share
> transfer capacity when several sequences compete, and hold the last valid
> frame whenever preparation loses the race.

Loaded does not mean decoded, and decoded does not mean permanently resident.

We had a 3D model that looked correct everywhere except the product.

The same `.glb` looked right in a standalone inspector. Its meshes, materials, and embedded texture
maps were all present. In the app, though, the material looked broken. That made the likely suspects
feel familiar: color space, environment lighting, post-processing, or a material override somewhere
after `GLTFLoader` returned.

None of them was the problem.

The browser had downloaded the GLB, but Content Security Policy blocked Three.js from turning the
images inside it into textures. The detail that made this hard to spot was that allowing `blob:` in
`img-src` was not enough. On the code path Three.js selected, those images were loaded with
`fetch()`, so the relevant directive was `connect-src`.

## A GLB is a container, not one indivisible resource

A binary glTF file can package several kinds of data into one response:

- scene and node definitions
- mesh buffers
- material parameters
- animations
- image bytes used by material textures

Seeing a successful request for `model.glb` only proves that the outer container arrived. It does
not prove that every resource inside the container completed the browser APIs needed to become a
renderable texture.

For an embedded image, Three.js' [`GLTFLoader`](https://github.com/mrdoob/three.js/blob/r183/examples/jsm/loaders/GLTFLoader.js)
roughly follows this path:

```txt
GLB response
  -> image bufferView
  -> Blob
  -> temporary blob: URL
  -> ImageBitmapLoader
  -> fetch(blob:...)
  -> createImageBitmap(...)
  -> Three.js texture
  -> GPU upload
```

The first surprising step is the temporary URL. When an image is stored as a `bufferView`,
`GLTFLoader` wraps its bytes in a `Blob` and calls `URL.createObjectURL()`. That produces a URL such
as `blob:https://example.com/63f...` which exists only long enough for the loader to decode it.

The second surprising step is the loading API. In browsers where `createImageBitmap` is available,
`GLTFLoader` prefers `ImageBitmapLoader`. Three.js' [`ImageBitmapLoader`](https://github.com/mrdoob/three.js/blob/r183/src/loaders/ImageBitmapLoader.js)
calls `fetch(url)`, reads the response as a blob, and passes it to `createImageBitmap()`.

That implementation detail decides which CSP directive applies.

## `img-src` does not govern every image-shaped thing

The policy already allowed blob images:

```txt
default-src 'self';
img-src 'self' data: blob: https:;
connect-src 'self' https: wss:;
```

At a glance, this looks correct. The resource is an image and `img-src` allows `blob:`. But CSP does
not classify a request only by the kind of data it eventually becomes. The loading mechanism and
request destination matter.

An HTML image load is governed by `img-src`. A script-level `fetch()` is governed by `connect-src`.
The [CSP specification](https://www.w3.org/TR/CSP3/#directive-connect-src) explicitly places
`fetch()` under `connect-src`.

So this request was denied:

```txt
fetch('blob:https://example.com/63f...')
```

The browser console contained the useful evidence—a CSP violation followed by Three.js reporting
that it could not load a `blob:` texture—but the visual result looked enough like a material problem
to send the investigation toward shaders and lighting first.

The minimal policy change was to allow the scheme in the directive used by that path:

```diff
- connect-src 'self' https: wss:;
+ connect-src 'self' blob: https: wss:;
```

For a cross-browser policy, keep `blob:` in `img-src` too. Three.js can fall back to a traditional
image loader when `ImageBitmapLoader` is unavailable, and that path is governed by `img-src` instead.
The same asset can therefore exercise different CSP directives in different browser environments.

This is not a reason to paste a permissive CSP into every Three.js project. Add only the source
schemes the application intentionally uses, to the directives that need them, and keep the rest of
the policy narrow.

## The inspector changed the debugging boundary

The decisive check was opening the production asset outside the application. The JOYCO
[GLTF inspector](https://hub.joyco.studio/toolbox/gltf) showed the same remote GLB with its expected
materials and texture maps.

That did not prove every aspect of the app renderer was correct. It proved something more useful:
re-exporting the model was no longer the next move. The investigation boundary shifted from asset
creation to application loading and rendering.

Use that split deliberately:

1. Open the exact production GLB in an independent inspector, not a local source file with the same
   name.
2. If it is wrong there too, inspect the export, material definitions, texture packing, and glTF
   extensions.
3. If it is correct there, inspect the app's console, network requests, CSP, loader configuration,
   renderer, and any post-load material mutation.

An independent viewer is not only a model viewer. It is a way to cut the system in half.

## Read the console before rewriting the material

The useful debugging order for “correct GLB, wrong app” is:

### 1. Look for blocked subresources

Search the console for `CSP`, `blob:`, `texture`, and the loader's error prefix. In the Network panel,
do not stop after finding a successful `.glb` response. Look for subsequent image, blob, decoder, and
worker requests.

### 2. Match the policy to the API actually making the request

Do not infer the CSP directive from the final resource type. Determine whether the loader uses an
HTML image, `fetch()`, a worker, media element, or another browser API on the failing path. Then check
`img-src`, `connect-src`, `worker-src`, or the corresponding directive.

### 3. Change one boundary at a time

If the console says the browser refused a texture request, changing metalness, roughness, output
color space, or environment intensity cannot restore the missing bytes. Fix the resource-loading
boundary first; evaluate the rendered material only after every expected map loads.

### 4. Reload the response policy

When CSP is delivered as an HTTP response header, a normal hot reload may not replace the document's
policy. Reload the full page after changing it; if the old header may be cached, use a hard refresh
and verify the active header in DevTools.

## Preserve the fix as a contract

CSP strings are easy to “clean up” later because a source such as `blob:` can look redundant next to
`img-src`. A small regression test should name why it exists:

```ts
test('CSP allows GLTFLoader to resolve embedded textures from blob URLs', () => {
  const connectSrc = contentSecurityPolicy
    .split('; ')
    .find((directive) => directive.startsWith('connect-src '))

  expect(connectSrc?.split(' ')).toContain('blob:')
})
```

That test protects the configuration contract. A browser-level check protects the behavior: load a
GLB with an embedded texture under the real response header, fail on CSP violations, and confirm the
texture request completes.

Both are useful. The unit test explains the otherwise odd-looking token; the browser test catches a
future loader or policy change that moves the request to a different path.

## When this can happen again

This bug needs a particular intersection: embedded glTF textures, a loader that turns them into
temporary object URLs, a `fetch()`-based image decoding path, and a restrictive CSP. Sites without a
meaningful CSP will never notice it.

Within WebGL applications that do enforce CSP, though, the class is repeatable. It can appear after:

- adding or tightening security headers
- moving textures from external files into a GLB
- upgrading Three.js or changing the texture loader
- testing in a browser that selects a different decoding path
- replacing a development server's headers with production headers

The lesson is broader than glTF: a successful container request does not prove its internal resources
survived every later browser boundary, and CSP follows the API performing the load rather than your
mental category for the resulting data.

## The rule

> When a GLB is correct in an independent inspector but wrong in the app, verify its subresource
> requests before touching the material. Embedded textures may become temporary `blob:` URLs, and if
> the loader fetches them, CSP must allow that scheme in `connect-src`, not only `img-src`.

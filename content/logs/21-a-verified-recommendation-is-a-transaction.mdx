There is a large difference between showing a recommendation and putting an **Apply** button on it.

Suppose an analysis tool says:

> Drop this item. Predicted error rate: 18% → 6%.

As text, this is advice: the user reads it and edits the state themselves. Once the product adds one-click Apply, it makes a much stronger promise:

1. The mutation applied is exactly the mutation that was analyzed.
2. It is applied to exactly the state the analysis described.
3. A double-click does not apply it twice.
4. Undo reverses every consequence, not only the most visible field.
5. The product re-checks the resulting state instead of trusting the prediction.

That is not a button handler. It is a transaction.

## The stringly-typed trap

Recommendation systems often begin with display data:

```ts
type Recommendation = {
  id: string
  title: string
  predictedValue: number
}
```

The analysis layer already constructed the candidate state, but it throws that state away after scoring it. Later, Apply tries to reconstruct the intended change from `id`, `title`, or a few parameters kept for display:

```ts
// DON'T
if (recommendation.id.startsWith('remove:')) {
  const targetId = recommendation.id.split(':')[1]
  removeItem(targetId)
}
```

Now there are two implementations of the recommendation: the one that produced the scored state, and the one that guesses how to reproduce it on click. They drift independently. The bug is quiet when the reconstruction is merely *similar*: the card claims the verified result is 6%, the click builds a state the analysis never saw, and the UI keeps presenting the old number as if it described the new state.

## Carry the mutation from the point where it is known

Make the concrete mutation part of the recommendation itself. Build it while the candidate's source objects are still in scope, then carry it unchanged through screening, ranking, rendering, and Apply.

```ts
type ApplyDescriptor =
  | { kind: 'remove'; targetId: string; expectedCount: number }
  | { kind: 'adjust'; targetId: string; expected: number; next: number }
  | { kind: 'advice-only' }

type Recommendation = {
  id: string
  predicted: Outcome
  apply: ApplyDescriptor
}
```

The descriptor is plain structured-clone-safe data, so it crosses a worker boundary without closures or an opaque identifier to re-parse. The same object that holds the predicted outcome holds the exact change that produced it. No stage downstream regenerates the candidate from a shorthand.

## Some verified advice must stay advice-only

Sometimes the analysis scores a candidate the persistent model has no faithful field for. It is tempting to approximate it on Apply. Don't. If the product cannot materialize the exact state it verified, the recommendation stays advice-only. **Applicability is a property of the model, not a presentation decision:** an Apply button is earned by round-trip fidelity.

## Reject stale recommendations at commit time

Verification may be asynchronous. While a worker scores candidates, the user can edit the very input the candidate depends on. The recommendation stays valid for the old state and becomes wrong for the live one. Abort signals help responsiveness but are not a correctness boundary; a worker can finish just as the abort fires.

Commit therefore needs optimistic concurrency control: serialize every input that gives the recommendation meaning, and require the live state to match when Apply runs.

```ts
const revisionKey = (state: State) =>
  JSON.stringify({ inputs: state.inputs, config: state.config })

function applyRecommendation(state, recommendation, expectedKey): ApplyResult {
  if (revisionKey(state) !== expectedKey) {
    return { ok: false, reason: 'stale' }
  }
  // apply the carried descriptor…
}
```

This is a compare-and-swap without a database: the worker computed against revision X, so the commit is allowed only while the app still describes revision X. Narrow preconditions on the changed entity are useful backstops on top. The principle is the same as an HTTP `If-Match` header: never commit a calculation against a version it never observed.

## Snapshot the whole mutation surface

A recommendation that appears to change one field may touch several stores. Undoing only the most visible one leaves the rest corrupted, and recording an inverse command per branch means every new side effect adds another inverse someone can forget.

For small client-side state, snapshot the entire slice the transaction is authorized to mutate:

```ts
type RecommendationTransaction = {
  recommendationId: string
  predicted: Outcome
  appliedKey: string
  before: MutableSlice
}
```

Apply computes the new slice and records the complete prior slice in `before`; Undo restores it, so every mirrored record moves back together. This is not "snapshot the whole app on every click." Define the mutation boundary deliberately: every store this class of recommendation can touch, and nothing outside it.

## Guard undo against time travel

Undo is another conditional write. Consider: apply a change, then manually edit something else, then click the old Undo receipt. Restoring the pre-apply snapshot would also erase the manual edit. So the transaction records an `appliedKey` for the state it produced, and Undo is offered only while the live state still matches it:

```ts
if (revisionKey(liveState) !== transaction.appliedKey) {
  return { ok: false, reason: 'state-drifted' }
}
return transaction.before
```

Derive the receipt and the Undo action from the same condition, so an intervening edit makes both disappear. No stale control waits to overwrite newer work.

## Idempotency has a window

A same-tick double-click can run the handler twice before the framework commits the first state change. A small in-memory guard keyed by `(revisionKey, recommendationId)` closes that window. It should not live forever: if the user later reverses the state and legitimately applies the same recommendation again, a permanent "already applied" flag would swallow a valid action. Reset it once input state commits; it covers the synchronous duplicate, not transaction history.

## The prediction is a receipt, not the new truth

The predicted outcome is what the analysis estimated *before* Apply. Once the state actually changes, the ordinary pipeline should run again and become authoritative. The strongest regression test closes that loop:

```ts
const applied = applyRecommendation(initialState, recommendation, initialKey)
expect(applied.ok).toBe(true)
expect(analyze(applied.next).tier).toBe(recommendation.predicted.tier)
```

That proves the analysis path and the mutation path still describe the same operation, something no unit test of either in isolation can show.

## When the full pattern is worth it

A synchronous, local toggle does not need this machinery. Reach for it when a recommendation is computed asynchronously, changes durable or multi-store state, carries a quantitative prediction, or can go stale while visible. The louder the claim ("verified," "safe," "will save 30%"), the more the transaction matters.

## The rule

> A one-click verified recommendation carries the exact mutation that was analyzed, commits only against the revision it observed, snapshots its full mutation surface, makes duplicate commits idempotent, guards undo against later edits, and re-analyzes the applied state as the new truth.

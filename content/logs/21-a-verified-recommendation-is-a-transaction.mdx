There is a large difference between showing a recommendation and putting an **Apply** button on it.

Suppose an analysis tool says:

> Remove one Ogre. Predicted death risk: 18% → 6%.

As text, this is advice. The user interprets it and edits the state themselves. Once the product adds
one-click Apply, it makes a much stronger promise:

1. The mutation applied is exactly the mutation that was analyzed.
2. It is applied to exactly the state that analysis described.
3. A double-click does not apply it twice.
4. Undo reverses every consequence, not only the most visible field.
5. The product checks the resulting state instead of treating the prediction as truth.

That is not a button handler. It is a transaction.

## The stringly-typed trap

Recommendation systems often begin with display data:

```ts
type Recommendation = {
  id: string
  title: string
  description: string
  predictedValue: number
}
```

The analysis layer has already constructed the candidate state, but it throws that state away after
scoring it. Later, Apply tries to reconstruct the intended mutation from `id`, `title`, or a few
parameters kept for display:

```ts
// DON'T
if (recommendation.id.startsWith('remove:')) {
  const monsterId = recommendation.id.split(':')[1]
  removeMonster(monsterId)
}
```

This creates two implementations of the recommendation. One implementation produced the state that
was simulated; another guesses how to reproduce it when clicked. They can drift independently.

The bug is especially quiet when the reconstruction is merely similar. The card says the verified
result is 6%, the click creates a state the simulator never saw, and the UI continues to present the
old estimate as if it described the new state.

## Carry the mutation from the point where it is known

The fix is to make the concrete mutation part of the recommendation itself. Build it while the
candidate's source objects are still in scope, then carry it unchanged through screening, worker
serialization, ranking, rendering, and Apply.

```ts
type ApplyDescriptor =
  | {
      kind: 'remove'
      monsterId: string
      expectedCount: number
      toCount: number
    }
  | {
      kind: 'weaken'
      monsterId: string
      expectedMultiplier: number
      nextMultiplier: number
    }
  | {
      kind: 'add-item'
      characterId: string
      itemId: string
    }
  | {
      kind: 'advice-only'
    }

type Recommendation = {
  id: string
  title: string
  predicted: Outcome
  apply: ApplyDescriptor
}
```

The descriptor is plain structured-clone-safe data. It crosses a web worker boundary without
closures, class instances, or re-parsing an opaque identifier. The same candidate object that holds
the predicted outcome holds the exact discrete change used to produce that outcome.

The recommendation now has identity all the way through the pipeline:

```txt
source state
  → candidate state + apply descriptor
  → screen
  → full verification
  → rank
  → render
  → apply the carried descriptor
```

No stage regenerates the candidate from a shorthand.

## Some verified advice must remain advice-only

One candidate in our system simulated a global one-round opening condition. The persistent encounter
model had no faithful field for that exact assumption. It would have been easy to approximate it on
Apply by attaching a similar condition to each enemy.

We did not.

If the product cannot materialize the exact state it verified, the recommendation stays advice-only.
This is an important consequence of treating Apply as a transaction: **applicability is a property of
the model, not a presentation decision.** An Apply button is earned by round-trip fidelity.

## Reject stale recommendations at commit time

Verification may happen asynchronously. While a worker simulates candidates, the user can add an
enemy, switch rulesets, change a character, or edit the same stat the candidate intends to change.
The recommendation can be perfectly valid for the old state and wrong for the live one.

Abort signals improve responsiveness, but they are not a correctness boundary. A worker may finish
just as the abort happens, a callback may already be queued, or the card may stay visible while other
state changes elsewhere.

Commit therefore needs optimistic concurrency control: hash or serialize every input that gives the
recommendation meaning, then require the live state to match it when Apply runs.

```ts
const revisionKey = (state: AnalysisState) =>
  JSON.stringify({
    party: state.party,
    encounter: state.encounter,
    ruleset: state.ruleset,
  })

function applyRecommendation(
  state: AppState,
  recommendation: Recommendation,
  expectedKey: string,
): ApplyResult {
  if (revisionKey(state) !== expectedKey) {
    return { ok: false, reason: 'stale' }
  }

  // Apply the carried descriptor...
}
```

This is a compare-and-swap without a database. The worker computed against revision X, so the commit
is allowed only while the app still describes revision X.

Broad revision equality is the first guard. Narrow preconditions on the changed entity are useful
backstops:

```ts
if (monster.count !== apply.expectedCount) {
  return { ok: false, reason: 'stale' }
}
```

For a composed stat edit, keep the original override in the descriptor and refuse to overwrite it if
the live override drifted. The principle is the same as an HTTP `If-Match` header: do not commit a
calculation against a version it never observed.

## Snapshot the whole mutation surface

A recommendation that appears to change one field may touch several stores. Giving a character an
item can update the active roster, guest copies, and an owned-items ledger. Undoing only the
character's loadout leaves the ledger corrupted. Recording an inverse command for each branch is
possible, but every new side effect creates another inverse that can be forgotten.

For small client-side state, snapshot the entire slice the transaction is authorized to mutate:

```ts
type RecommendationTransaction = {
  recommendationId: string
  summary: string
  predicted: Outcome
  appliedKey: string
  before: MutableSlice
}
```

Apply computes a new immutable slice and records the complete prior slice in `before`. Undo restores
that snapshot, so every mirrored record moves back together.

This does not mean snapshot your whole application for every click. Define the mutation boundary
deliberately: every backing store this class of recommendation can touch, and nothing outside it.

## Guard undo against time travel

Undo is another conditional write. Imagine this sequence:

1. Apply “remove one Ogre.”
2. Manually add a Dragon.
3. Click the old Undo receipt.

Restoring the pre-apply snapshot would also erase the Dragon, even though it was not part of the
transaction. So the transaction records an `appliedKey` for the state it produced. Undo is offered
only while the live state still matches that key:

```ts
if (revisionKey(liveState) !== transaction.appliedKey) {
  return { ok: false, reason: 'state-drifted' }
}

return transaction.before
```

In the UI, the receipt and Undo action can be derived from the same condition. As soon as the user
makes an intervening edit, both disappear. There is no stale control waiting to overwrite newer work.

## Idempotency has a window

A same-tick double-click can run the handler twice before React commits the first state change. A
small in-memory guard keyed by `(revisionKey, recommendationId)` makes that window idempotent.

The guard should not live forever. If the user later reverses the state manually and legitimately
applies the same recommendation again, a permanent “already applied” flag would silently ignore a
valid action. Reset the guard after input state commits; it exists to cover the synchronous duplicate
window, not to become transaction history.

## The prediction is a receipt, not the new truth

The recommendation's predicted outcome is what the analysis estimated before Apply. Once the real
state changes, the ordinary analysis pipeline should run again and become authoritative. This
distinction matters when the simulator is stochastic, when user-authored overrides compose, or when
the live app contains derived state.

The strongest regression test closes the loop:

```ts
for (const recommendation of verifiedRecommendations) {
  const applied = applyRecommendation(initialState, recommendation, initialKey)
  expect(applied.ok).toBe(true)

  const actual = analyze(applied.next)
  expect(actual.tier).toBe(recommendation.predicted.tier)
}
```

That test proves the analysis implementation and the mutation implementation still describe the same
operation. A unit test for each one in isolation cannot prove that.

## When the full pattern is worth it

A synchronous, local toggle does not need this machinery. Reach for it when a recommendation is
computed asynchronously, changes durable or multi-store state, carries a quantitative prediction,
or can become stale while visible. The higher the product's claim (“verified,” “safe,” “optimized,”
“will save 30%”), the more important the transaction becomes.

## The rule

> A one-click verified recommendation carries the exact mutation that was analyzed, commits only
> against the revision it observed, snapshots its full mutation surface, makes duplicate commits
> idempotent, guards undo against later edits, and re-analyzes the applied state as the new truth.
